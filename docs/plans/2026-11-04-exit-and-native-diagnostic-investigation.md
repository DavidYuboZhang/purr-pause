日期：2026-11-04（Asia/Shanghai）。本文件保留已批准方案；本轮有边界实验和现场恢复已完成，旧退出仍属历史证据不足；实际结果与偏差见 [执行报告](../baselines/2026-11-04-exit-and-native-diagnostic.md)，本轮没有新增产品修复。当前进展见 [STATUS.md](../../STATUS.md)，前期事实与原始证据见 [基线报告](../baselines/2026-11-03-mvp-baseline.md)。沿用 PP 环境与现有未提交暂停修复，不重建 tasks 或平行状态清单。

## 1. 目标与范围

分别定位两项问题，再判断是否存在因果联系：

- A：PID 33080 在用户未主动退出时消失，缺少退出码；区分应用自身退出、执行会话/进程组终止、外部终止及其他未知原因。
- B：动画淡出测试输出 `0x8001010d`，但用例和进程继续成功结束；查明异常触发层、诊断输出层及是否有可见功能影响。

先采证和单变量对照，再按证据确定最小修复。执行排查阶段默认不改产品源码、原测试断言、PP 依赖、版本或配置格式，不升级系统/Qt，不构建、提交或发布。临时启动器、最小复现、日志和必要原生调试输出置于新的本地证据目录；验证可读结论存入 docs。定位后若需修复，单独列出具体改动与验证范围；不以屏蔽输出或禁用功能作为解决。

## 2. 已知事实、证据缺口与候选解释

| 事项 | 已确认 | 尚不能断言 |
|---|---|---|

| 调试工具 | cdb、windbg、procdump 未在当前 PATH 查到 | 不能等同于整台机器未安装；如需使用先只读查安装目录 |

### 官方实现给出的排查线索

- 微软将该码定义为 `RPC_E_CANTCALLOUT_ININPUTSYNCCALL`，涉及输入同步调用期间的外部调用限制；错误码本身不能确定调用来自哪层。[Microsoft 错误码](https://learn.microsoft.com/en-us/windows/win32/com/com-error-codes-3)
- 本机安装的 `_pytest/faulthandler.py` 在配置时启用 faulthandler；官方也说明 pytest 默认启用该插件。[pytest 文档](https://docs.pytest.org/en/stable/how-to/failures.html#fault-handler)
- CPython 3.11.18 Windows 异常处理器可打印 “Windows fatal exception” 并转交后续处理器。因此存在“记录了原生异常，但后来被处理且进程继续”的可能；是否为本机实际链路仍须实验验证。[匹配 Python 版本的源码](https://github.com/python/cpython/blob/v3.11.18/Modules/faulthandler.c#L358-L417)
- Qt 6.12.0 的 `handleWmGetObject()` 会调用 `UiaReturnRawElementProvider()`；UI Automation/可访问性属于候选触发路径，不能仅凭源码存在就认定它触发了本次异常。[Qt 版本源码](https://github.com/qt/qtbase/blob/v6.12.0/src/plugins/platforms/windows/uiautomation/qwindowsuiaaccessibility.cpp#L33-L50)
- Windows 支持把子进程与父任务对象分离，但取决于任务对象设置；控制台分离、进程组和任务对象是不同条件，不能只观察父 PID 就认定生命周期独立。[Microsoft 创建标志](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)

候选解释保持并列：A1 执行会话/Job/控制台生命周期；A2 Qt 主事件循环退出或 Python 回调异常；A3 原生异常导致终止；A4 系统或外部终止。B1 已处理的 COM 异常被 faulthandler 报出；B2 Qt/UIA 或外部观察工具触发；B3 显示、透明、淡出、销毁顺序或测试嵌套事件循环的组合；B4 依赖兼容性。以上均为待验证假设。

## 3. 执行顺序与检查点

顺序为 P0 → B1/B2 → A1/A2 → C。优先查可稳定重现的单用例，同时为较长的进程观察准备同一套证据格式；各实验逐个执行，避免多个透明窗口或观察工具互相干扰。

| 阶段 | 任务及依赖 | 验收条件 |
|---|---|---|
| P0 | 固定证据和观测入口，无前置依赖 | 解释器/Qt/插件/代码哈希、配置字节、已有实例、启动参数及观测边界完整；正常退出控制能留下退出码 |
| B1 | 诊断来源与最小复现，依赖 P0 | 默认单用例复现频率、诊断是否出现、退出码及 finished/销毁结果齐全；能区分输出机制与触发事件 |
| B2 | 单变量定位与必要原生栈，依赖 B1 | 最小触发条件或明确不可复现条件；如指向 UIA/COM，取得模块/异常处理层证据，而非只看 Python 等待栈 |
| A1 | 启动生命周期控制，依赖 P0 | 普通探针与 PP 各自的父/子/Job/会话状态、退出记录可对照；只结束本轮测试父会话 |
| A2 | PP 操作与静置观察，依赖 A1 | 正常退出、提前关闭、暂停/保存/继续等路径有时序记录；意外退出如重现，有退出码/异常/外部证据，否则记未复现 |
| C | 关联判断、修复建议及收尾，依赖 A/B 结果 | 两项分别分类、因果关系有证据或明确未知；配置和进程恢复；更新报告与 STATUS |

检查点一（P0+B1 后）：若问题不再复现，保留每次结果与条件，先检查会话/观测差异，不盲目升级依赖。检查点二（A/B 定位后）：依据证据选择最小修复，不提前扩展为全项目重构。检查点三：若确有代码或依赖改动，再执行受影响回归、完整套件及必要桌面复验。

## 4. P0：统一证据与独立观测

1. 重新核对分支、工作区和现有 4 份源码/测试改动的字节；记录 Python 3.11.18、PyQt6/Qt 6.12.0、pytest 9.2.0、pytest-qt 4.5.0，相关 Windows Qt 插件与模块路径。仅记录必要环境字段，不全量导出环境变量或含私密参数的进程命令行。
2. 新建带日期的证据目录，保存配置存在性、原始字节/哈希、当前显示环境及已有 PP 进程。旧证据保持只读；空结果也显式写成 `[]`，并记录查询权限、时间和成功/失败状态，区分“无记录”和“查询失败”。
3. 外部监测进程独立于被测父会话，记录 PID、创建时间、父 PID、Session ID、可查询的 Job 成员状态、启动模式、UTC 时间和单调时间；以创建时间/进程句柄避免 PID 复用。持续监测退出码和日志，不仅在退出后查询 PID。
4. 仅在临时诊断入口记录 QApplication 的 aboutToQuit/lastWindowClosed、退出返回、Python 异常钩子、atexit，以及窗口显示/finished/销毁阶段。保存原处理链并继续调用，不吞异常、不改变退出/暂停语义；诊断开关与未插桩对照分开。
5. 对本轮实例做一次已知的托盘正常退出控制，确认日志/退出码能闭环。突然结束时缺少 atexit 或 aboutToQuit 只能作为线索；退出码 0 本身也不单独证明正常退出。

## 5. B：0x8001010d 的最小实验矩阵

先在原 PP 环境、Windows 原生 Qt 平台运行一个已知用例，保留原断言与完整 stderr。默认先 1 次；如需判断稳定性，每条件预先安排 3 个独立进程，保存全部结果并记录“出现次数/总次数”，不靠重跑挑一次通过。每次新 basetemp，并保留退出码。

```powershell
$env:PYTEST_QT_API = 'pyqt6'
$env:QT_QPA_PLATFORM = 'windows'
$env:PYTHONUTF8 = '1'
python -m pytest -v -ra tests/test_cat_anim_window.py::test_request_finish_starts_fade_and_emits --basetemp '<新的目录>'
```

按结果推进，每次只改变一个因素：

| 对照 | 要区分什么 | 证据要求 |
|---|---|---|
| 默认 pytest vs 同用例临时 `-p no:faulthandler` | 诊断输出是否来自 faulthandler | 输出有无、用例/进程结果同时记录；关闭插件只作诊断，不能作为修复或通过标准 |
| pytest 外最小 Qt 程序，分别启用/不启用 faulthandler | pytest/pytest-qt 嵌套等待是否必要 | 同样 show→request_finish→finished→销毁；保留 Qt 主循环的正向完成控制 |
| 当前 CatAnimWindow vs 普通 QWidget 的显示/透明/opacity 淡出 | 问题是否需要素材模型或特殊窗口属性 | 使用隔离最小复现，每步单因素增减，不改正式测试；记录异常频率及窗口生命周期 |
| 保持其他条件，单独比较点击穿透设置、是否显示窗口、fade 与关闭时序 | Windows 原生窗口样式/动画/销毁是否必要 | 改动只在临时副本或诊断入口；移除某条件后不出现并不足以直接批准删除产品功能 |
| 无主动 UIA 查询 vs 对本轮 HWND 的受控 UIA 查询 | 可访问性/外部观察是否触发或放大 | “未主动查询”不等于系统没有其他 UIA 客户端；只记录自己的查询与 WM_GETOBJECT 时间，避免归咎任一后台程序 |

若仍不能定位，用现有可用的原生调试器在独立子进程捕获该异常的首次机会调用栈及继续后的状态，记录异常码、线程、模块/符号、能否被后续处理器处理、最终退出码；必要时取得未处理异常栈。先查工具安装位置；若确需补充工具，说明具体用途与安装范围，不修改 PP 环境清单或系统 Python。

初步关注模块包括 UIAutomationCore、COM、Qt Windows 平台层、Python/faulthandler；只有栈证据吻合才定位至该层。避免通过 Python 回调直接接管原生异常分派；不吞 `0x8001010d`，不永久关闭 faulthandler、Qt 可访问性、动画、系统辅助功能或安全工具。无界面平台只作辅诊，不替代 Windows 平台结论。

## 6. A：旧实例意外退出的受控排查

### A1：先验证启动边界

- 用仅写心跳的专用探针，对比“原执行会话持有”和“独立外部监测”两种启动方式。记录父/子/会话/Job 状态；只让本轮短命测试父会话正常结束，检查探针是否被连带终止。监测必须在被测生命周期之外。
- 再以相同入口、解释器、配置、权限和操作序列对比 PP 的两种启动方式；不要把 runpy/direct-main、权限、重定向、进程组和 Job 分离一次全部改变。必要时逐项分解现有两个启动器的差别。
- 若本执行器无法受控重现原会话终止语义，明确记录限制；普通父进程退出实验不能冒充相同 Job/控制台事件。不要关闭 Codex、注销、重启或操作用户工作终端来强造复现。
- 验证 Job 条件对探针和 PP 的一致影响，才支持生命周期解释；仅“独立启动没有退出”不能确定根因。旧退出的确切原因若无历史事件，可能只能保留未知。

### A2：再观察应用自身路径

采用独立监测、Windows 桌面真实实例；每次记录实际操作的时间点：启动、设置、暂停、暂停保存、继续、自然结束、提前关闭、静置和托盘退出。至少覆盖 3 轮提醒，初次每种启动条件观察上限 15 分钟，用户离开时按事先约定保留或暂停，不擅自清理等候中的现场。

观察没有复现时仅记该条件和时长“未复现”。旧实例跨越数小时，15 分钟通过不能排除长时问题；如证据提示需延长，另约明确观察窗口与结束条件，不无限运行。

重新读取时间窗口内的应用错误/系统会话相关记录，以精确 PID/创建时间/可执行文件对齐；不预设事件 ID 必定存在，不开启全局审计或注册表崩溃转储。诊断程序只观察本轮进程，不结束或附加到用户已有应用。

## 7. 关联判断与修复门槛

| 实验结果 | 允许的结论与下一步 |
|---|---|
| 普通探针和 PP 均随已确认的会话/Job 事件退出，独立方式不退出 | 支持启动生命周期因素；改善开发/验收启动方式，不能据此声称旧事件已逐秒还原 |
| aboutToQuit/退出调用先发生，随后主循环返回 | 沿 Qt 退出触发者或 Python 回调异常链定位；保留具体触发栈再设计最小修复 |
| 原生异常未处理并导致本轮 PP 终止 | 以原生栈及实际退出码定位代码/Qt/环境；不能仅由非零退出码判定崩溃 |
| 同一码发生后事件循环、销毁与退出控制正常 | 支持已处理异常/诊断噪声解释，但仍需确定来源和用户影响；不以隐藏文本完成修复 |
| B 可重现但 A 未重现，或二者触发条件不同 | 分别报告，暂不建立因果联系；旧退出保留证据不足 |

若需将两项关联，至少要在同一次被监测的 PP 退出中对齐该码、原生调用链、终止/退出路径与时间，排除同时发生的生命周期终止。相同时间附近、相同 Windows 环境或相同“fatal”字样都不足以证明因果。

有证据的业务缺陷采用最小修复和先失败回归；依赖问题如需版本对照，使用独立临时环境、一次一个版本，保留 PP 原环境，只有选择正式采用时才同步 environment.yml。原完整 87 项仅在实际代码/依赖改变或新证据需要时重跑；没有改动则不重复整套测试。无法复现的旧退出可交付有边界的“未复现/证据不足”，不伪称修复。
