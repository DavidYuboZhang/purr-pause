# PP 暂停状态一致性修复计划

日期：2026-11-03（Asia/Shanghai）。本文件保存已批准的修复方案；代码、自动化及计划内真实桌面回归已完成，现场已恢复；独立异常与验证限制见基线报告。当前进展统一见 [STATUS.md](../../STATUS.md)，行为决定见 [D-005](../../DECISIONS.md#d-005)。

## 1. 问题与目标行为

保留 [现状基线与桌面验收报告](../baselines/2026-11-03-mvp-baseline.md) 的原始失败记录，分别处理两条证据：

1. 已复现的代码问题：`SettingsDialog._save()` 总会发出间隔信号，托盘处理器调用 `RestTimer.reset()`，清除暂停并重新计时，却不更新菜单。
2. 已确认的桌面失败：用户报告暂停约一分钟后新出现动画，菜单显示“继续”。未取得当时进程内的计时状态，不能直接认定由问题 1 导致；修复后必须独立回归该现场场景。

用户已确认：**同一运行实例内，暂停期间保存设置必须保持暂停，只有明确点击“继续”才恢复计时。**

| 操作 | 计时器与提醒 | 托盘菜单 |
|---|---|---|
| 点击暂停 | 停止工作计时，阻止新的周期提醒 | 继续 |
| 暂停时保存相同设置、改间隔或只改休息时长 | 保存参数，保持暂停，底层 QTimer 不运行 | 继续 |
| 暂停时再次调用启动或更新间隔 | 不隐式恢复计时 | 继续 |
| 点击继续 | 使用最新工作间隔重新开始完整一轮，不补发暂停期间的提醒 | 暂停 |
| 运行中保存设置 | 保留现有重置规则：从保存后的完整工作间隔重新计时 | 暂停 |
| 取消设置 | 配置及计时/暂停状态不变 | 保持原状 |

暂停只阻止新提醒，已开始的休息仍可自然结束或由用户关闭。暂停状态不新增配置持久化，重启仍沿用当前默认运行行为。此次不调整动画、休息卡片、目录、依赖、发行流程或版本号。

## 2. 最小实现与接口

### 计时器：统一状态规则

实施时主要改动根目录 `timer.py`；目录整理后的当前位置为 [core/timer.py](../../purr_pause/core/timer.py)。以下保留当时方案：

- `reset(interval_minutes)` 更新间隔并停止旧计时；保留当前暂停标志，仅非暂停时重新启动 QTimer。
- `start()` 遵守暂停状态，不能在暂停标志为真时启动底层计时；初次启动及运行中的调用保留原用途。
- `pause()` 确保底层计时器停止；`resume()` 是同一实例内唯一清除暂停的正常入口，恢复时使用最新完整间隔。
- 新增 `paused_changed(bool)` 信号，仅在真实暂停状态变化时发出；现有 `rest_due`、方法名称和参数不变。
- 保证“暂停为真 ⇒ QTimer 不活动”；不通过菜单文字反推模型状态，不增加第二套暂停标志。

### 托盘：从模型同步菜单

实施时主要改动根目录 `tray.py`；目录整理后的显示层位置为 [ui/tray.py](../../purr_pause/ui/tray.py)，业务协调已迁至 [controller.py](../../purr_pause/controller.py)。以下保留当时托盘直接连接计时器的方案，不代表当前接口：

- 创建菜单时根据 `timer.is_paused` 设置初始文字，并连接 `paused_changed(bool)`。
- 通过一个同步方法生成“暂停/继续”文字；切换处理器只调用模型的暂停或继续，不再另行维护菜单状态。
- 保存设置继续使用现有处理路径，由修正后的 `reset()` 保持暂停；不改变设置对话框现有信号协议或配置格式。

Qt 官方文档说明 `stop()` 停止定时器，`isActive()` 表示实际运行状态；运行时修改 interval 也可能重新启动计时。因此验证必须同时检查模型标志、底层活动状态与菜单，不能只看文字。[QTimer 官方文档](https://doc.qt.io/qt-6/qtimer.html)

## 4. 自动化测试矩阵

在 PP 环境使用 pytest + pytest-qt，临时配置重定向到测试目录，不写用户配置；使用真实 Qt 计时器和实际信号连接，隐藏测试托盘图标以免干扰桌面。

| 场景 | 必须证明的结果 |
|---|---|
| 直接暂停跨多个缩短后的计时周期 | 不发出 `rest_due`，暂停标志为真且 QTimer 不活动 |
| 暂停后保存相同设置 | 配置正确，暂停持续，菜单为继续，不发新提醒 |
| 暂停后改变工作间隔 | 新间隔生效但不启动计时；点击继续后使用新间隔 |
| 暂停后只改休息时长 | 新休息时长保存；即使对话框同时发出间隔信号也不恢复计时 |
| 暂停后调用 `start()` 或多次 `reset()` | 不激活定时器、不清除暂停 |
| 取消设置 | 文件字节和暂停状态均不变 |
| 运行中保存设置 | 保持运行、使用预期间隔，菜单为暂停 |
| 连续暂停/继续及重复调用 | 不产生相反状态或重复提醒源；仅真实状态变化发出 `paused_changed` |
| 托盘创建前模型已暂停，或模型被直接暂停/继续 | 初始及随后菜单均随模型正确同步 |
| 继续后的正向控制 | 能再次发出提醒，防止用“永久停止”伪装修复 |

计时测试使用短周期和 pytest-qt 的事件等待；先证明计时器能够发信号，再检查暂停跨多个周期不发信号。组合保存测试断言真实状态和持久化结果，不仅断言函数调用次数。现有断言不削弱、不跳过失败。

执行命令（已激活 PP；每次使用全新的可写 basetemp）：

```powershell
$env:PYTEST_QT_API = 'pyqt6'
$env:QT_QPA_PLATFORM = 'windows'
python -m pytest -v -ra tests/test_timer.py tests/test_tray.py tests/test_settings.py --basetemp '<新的局部测试目录>'
python -m pytest -v -ra --basetemp '<新的完整测试目录>'
```

先运行局部 RED/修复后的 GREEN，再运行一次完整套件；仅在新改动或失败需要时重跑。测试结果记录通过、失败、错误、跳过和耗时。

## 5. Windows 人工回归、异常处理与交付

继续采用“用户人工点击、助手核验”。开始前新建配置原始字节/存在状态快照，记录 PID、主屏和缩放；保持一个可持续运行的交互桌面实例，每次等待回复时不自行退出。

按顺序回归：

1. 设置 1 分钟／20 秒，等待已有休息结束，再直接暂停。确认菜单显示继续并收起菜单；助手从用户确认后计时至少 75 秒，用户全程观察无新卡片或动画。未明确通知前不点击继续。
2. 保持暂停，依次保存相同设置、只改休息时长（再恢复 20 秒）、把间隔改为 2 分钟后改回 1 分钟。每次保存后菜单均须保持继续；最后一次保存后再观察至少 75 秒，无新提醒。
3. 明确点击继续，确认菜单变为暂停；1 分钟配置下在 90 秒排查时限内应重新出现提醒。完整观察自然结束、提前关闭后下一轮恢复，并以未保存的空白记事本复核焦点及点击穿透。
4. 用户从托盘退出并关闭本轮测试内容；助手确认所有本轮进程结束，配置恢复原始字节或原本不存在的状态，AppData 未变，环境与无关文件未被改变。

90 秒是排查界限，不是计时精度指标。任何新卡片或动画出现，都先确认暂停前是否已有休息、期间是否保存/继续、有无重复实例；不将旧动画延续当成新提醒。

若真实桌面暂停仍失败，不能关闭该缺陷或将基线改为通过。下一步在独立本地诊断启动器中透明记录实际操作前后的 PID、时间、暂停标志、QTimer 活动状态、间隔、菜单文字和 `rest_due` 事件；不记录用户文件内容或增加永久遥测。与用户观察对齐后再定位另一路原因，不能因为隔离测试通过就宣布现场已修复。

只有新增回归、原完整套件和以上真实桌面回归均通过，且现场恢复完成，才记录“暂停修复已验证”。详细证据追加到原基线报告的修复回归章节，不覆盖旧失败；STATUS 保存当前摘要，重要行为约定记录在 DECISIONS。
